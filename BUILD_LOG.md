## Oct 18 — the pop-up timing checks made event-based (and the exit cut-off they found); hourly cards in the place's zone

**1. The flaky check.** polish-check sampled each pop-up every 20 ms for 320 ms after the tap and looked for the two-frame "opening" position or an opacity still below 1; under production latency the tap could resolve after the whole 150 ms transition, so the samples saw only the end state (the chooser check failed once in the production smoke, and once in a dry run). Now the suite arms a MutationObserver before each tap: it records the element's data-state and computed opacity the moment it is inserted (the observer runs before the next paint, so this is the true start position whatever the latency), every data-state change, every `transitionend` / `animationend` on the element, and its removal; the check then waits for the event, not a fixed time. Nothing was loosened: an open must be inserted at "opening" below opacity 1 and end its opacity transition in "open" at 1; a close must pass "closing" and end its opacity transition at 0 before the element is unmounted; the pulse must end its 300 ms animation before removal. **This stricter version found a real defect:** closes were unmounted by the 150 ms timer a frame before the opacity transition ended (no `transitionend` ever fired on production), so every exit was cut short by up to one frame; the pulse's 340 ms timer likewise. Fix: `usePresence` unmounts on the element's own `transitionend` for opacity (the timer is only a 300 ms fallback, and Reduce Motion stays instant), and the pulse marker is removed on `animationend`. Five runs in a row against the preview with the fix are recorded below; against production (which still has the cut-off) the strict check fails as it should.

**2. Hourly cards in the place's zone.** The card clocks and day labels now use the forecast's resolved time zone (`r.data.timezone`, the one the 7-day list uses for "Today"), not the device's; midnight is the place's midnight. A card with a day label is wide enough for one line, so the strip's height is the same for every span (208 px, the placeholder matches). ## Oct 12 — air monitors (EPA AirNow sites): the client, ahead of the server

**Why a server after all:** AirNow's public files (`files.airnowtech.org/airnow/today/monitoring_site_locations.dat`, 3.2 MB, and `HourlyData_<UTC hour>.dat`, ≈ 0.7 MB an hour) are readable from the browser (CORS `*`, no key), but they carry raw hourly concentrations, not AQI — AirNow's site AQI is NowCast over the last 12 hours — so colouring a monitor correctly needs the keyed API (`/aq/data/` with `dataType=B` returns AirNow's AQI per site). The user decides which server hosts the key; nothing server-side was created.

**Client (built against a service contract, `src/api/airnow.ts`):** `GET <service>/sites?bbox=w,s,e,n` → `{ fetchedAt, sites: [{ id, name, agency, lngLat, parameters, readings: [{ parameter, value, unit, aqi, time }] }] }`, `time` = the END of the observation hour. The service URL comes from `VITE_MONITOR_SERVICE` at build time or `localStorage stormscope.monitorService` at run time (the mocked suites set it); with neither, the layer reports "Monitor service not set up yet" and makes no request — the state the preview shows until the server exists. "Air monitors (AirNow)" is a toggle in the Points group (`MonitorSitesLayer`): every site in view, one request per view, cached 10 min; a site with a reading under 2 h (from the end of its hour) is a dot in the EPA colour of its worst fresh reading; stale or offline sites are grey outlined dots (transparent fill), so a broken monitor is visible; tapping lists the name, what the site measures, each reading with AQI, category, value, age (stale ones marked) and the distance from the selected place, credited "EPA AirNow and the reporting air quality agencies · preliminary data" (the Data Exchange Guidelines, August 2025: preliminary, unaltered, credited, EPA colours). The legend carries both dot styles.

**AirNow limits and guidelines, for the service:** the API FAQ states a per-service hourly cap per key ("the web service will not return data until the next hour" once met; the number sits in each service's documentation behind the login, not verified here), observations updated once per hour and available 10–30 minutes past the hour, "cache daily or hourly air quality observation or forecast data". The Data Exchange Guidelines require: preliminary and subject to change, not for regulation; credit the agencies and EPA AirNow; values and advisories unaltered; EPA AQI colours; displays must say the data are preliminary; users must be told that products rely on the data. The service design: one upstream bbox request per ~0.25° tile per 10 minutes at most, a 10 min cache, a hard 2 h age rule measured from the end of the observation hour (the 02:00 observation for Johnston was 1 h 58 min old at 03:58 UTC — a strict window from the start of the hour would drop the current reading for part of every hour).

## Hardest parts, in order

1. **Dead / changed upstream APIs.** The brief named the USGS Water Services instantaneous-values API; `waterservices.usgs.gov/nwis/iv` now refuses connections (decommissioned). Replaced with the USGS Water Data OGC API (`api.waterdata.usgs.gov/ogcapi/v0`), which has a different shape (one feature per *time series*, not per site) and needs a second collection for names. NOAA NWPS keeps flood thresholds only on the per-gauge detail endpoint, so "categories for every marker" costs N+1 requests — solved with a nearest-20 cap, 5-way concurrency and a session cache. RainViewer's public tiles silently return a "Zoom Level Not Supported" image above z7; this only showed up in screenshots, and the fix is capping the raster source at `maxzoom: 7` so MapLibre overzooms.

2. **MapLibre 6 + Vite workers.** MapLibre 6 resolves its worker relative to `import.meta.url`, which breaks both under Vite's dependency pre-bundling (dev) and Rollup chunking (prod). The map rendered black with "Worker failed to load". Fix: import the worker via `?worker&url` and hand it to `setWorkerUrl()`. A second black-map cause was `maplibre-gl.css` overriding my container positioning (`.maplibregl-map { position: relative }` → 0 px tall) — fixed with a more specific selector.

3. **Flood-risk model that is honest and cheap.** Combining three datasets of different resolutions (9×9 Open-Meteo grid, z11 terrain tiles, thousands of NHD segments) into a 28×28 grid on a phone. Everything runs in a worker: terrarium PNGs are decoded with `OffscreenCanvas`, drainage distance uses an exact spherical point-to-segment formula with a bbox pre-filter (784 cells × ~2000 lines would otherwise be ~1.5 M segment tests). Weighting the factors so dry forecasts never light up (rain gate) and so non-US locations still get a meaningful terrain+rain score took several iterations against real locations (Philadelphia dry vs. Manchester in rain).

4. **Nowcast without a nowcast API.** Open-Meteo has no minute-scale nowcast, so the 6-hour nowcast is built in the worker: hourly cloud/rain/wind fields are interpolated to 10-min frames and advected semi-Lagrangian by the wind (with a steering factor and a blend that trusts the model near t0 and advection further out). Rendering: clouds+rain go through a MapLibre `canvas` source, wind through a separate particle canvas so the map itself doesn't repaint 60×/s. `animate: true` on the canvas source made the whole map re-render continuously; switching to `animate: false` + `play()/pause()` around a single frame fixed it.

5. **Popups that can't fall off a phone.** MapLibre's own popup overflows small viewports. The popup is React-rendered, measured, flipped above/below the tap point and clamped to the map container with an 8 px margin, and re-positioned on every `move`. Verified by tapping all four corners in the QA script.

6. **Keeping the map usable while panels are open.** The bottom sheet (peek / half / full) must never cover controls: the FAB, legend, toasts and MapLibre controls are positioned from a `--sheet-h` CSS variable that follows the sheet, and the full-height mode hides the floating controls (the ▼ button brings them back). The first QA run caught the FAB being buried under the half sheet.

7. **Verification with a hidden window.** The desktop's embedded browser pane stops painting when the app is minimised, so screenshots timed out. Switched to headless Playwright + SwiftShader (`scripts/e2e.mjs`, `scripts/qa.mjs`, `scripts/pwa-check.mjs`) for repeatable visual + functional checks.

## Round 3 — block tiling (Sept 30)

## Round 8 — condition codes, traffic guard, docs (Oct 1)

**RWIS status semantics (user item 1).** The user's reading was right. The DOT networks use the SCAN/ScanWeb surface-status table (Surface Systems → Vaisala); the direct ScanWeb glossary mirrors (`rwis.cotrip.org`, `rwis.mdt.mt.gov`, and a dozen other state hosts) refuse connections from this network, but Montana DOT republishes the same table on its main site: https://mdt.mt.gov/travinfo/atms-glossary.aspx. Verbatim: *Ice Warning* — "Continuous film of ice and water mixture at or below freezing (32°F / 0°C) with insufficient chemical to keep the mixture from freezing"; *Ice Watch* — "Thin or spotty film of moisture at or below freezing (32°F / 0°C)"; *Chemical Wet* — "Continuous film of water and ice mixture at or below freezing … with enough chemical to keep the mixture from freezing"; *Frost* — "Moisture on pavement at or below freezing … with a pavement temperature at or below the dew point temperature"; *Snow/Ice Warning* — "Continuous film of ice and water mixture at or below freezing … with insufficient chemical". Mapping now (`src/api/rwis.ts`): any *Warning*, *Frost*, plain Ice/Snow/Slush/Icy/Snowy → `ice` (can confirm); *Ice Watch* / *Snow Watch* → new `watch` state (possible ice only, never confirms; new `ice-watch` road status and "Possible ice — *station* reports Ice Watch" label); Chemical Wet / Wet / Damp / Trace Moisture / Moist / Dew → `wet`; Dry → `dry`; Other / No Report / NA / blank → `unknown`. **Phone sheet root cause (reproduced with CDP touch events, 390×844, DPR 3, before any change):** (1) the only visible collapse control, the ▼ button, sat at the end of the horizontally scrolling tab row at x = 404 on a 390 px viewport — off screen, so taps on it hit nothing; (2) dragging the content down (the gesture people try on phones) did nothing even at scroll top; (3) the handle did work in Chromium emulation, but it was a 17 px strip whose tap *cycled* peek → half → full → peek, so from half a tap made the sheet bigger; (4) the browser back gesture left the app. Fix (`BottomSheet.tsx`, `index.css`): the ▼ button is pinned outside the scrolling `tablist` inside the right safe‑area inset; the handle is a 30 px target whose tap toggles open/closed (drag or Arrow keys step through sizes), and the drag finishes on window listeners so a finger sliding off still counts; a downward swipe on content that starts at scroll top collapses one step; an expanded sheet owns one history entry so back collapses it (our own `history.back()` on UI collapse is ignored by the popstate handler); the toggle reacts on pointer‑up because Chromium swallows the click of a tap that follows a fling.
