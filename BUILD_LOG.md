## Oct 9 — the layers panel: iPhone overflow, desktop button under the rail

**Bug 1 (iPhone Safari, Map):** the open layers panel covered the place pill, ran off the top, and its first row could not be reached. Cause, measured before any change (Chromium 390 × 844, no insets): `.fab-menu` was bottom-anchored above ☰ inside `.fab-stack` with `max-height: calc(100vh − dock − 180px)` — a fixed budget that ignored the bottom nav (58 px), both safe-area insets and the top bar's real height, and used 100vh, which on iOS Safari is the *largest* viewport (toolbar collapsed). It already overlapped the pill by 12 px in Chromium; iPhone insets add ≈ 80 px and the expanded toolbar another ≈ 80 px, all of it going upward over the pill and off-screen. The hypothesis (bottom-anchored + vh) was right; the budget was short even without the vh problem. Fix (`index.css`, `SearchBar.tsx`): the chrome is described by variables on `.app` — `--topbar-top`, `--topbar-h` (published by SearchBar from the bar's real height, like `--playbar-h`), `--fab-h`, `--fab-gap`, `--fab-margin`, `--fab-stack-bottom` / `--fab-stack-top` (the stack's offsets, with the nav added on narrow map screens), `--menu-top-reserve` / `--menu-bottom-reserve` (safe areas + chrome + 8 px) and `--vvh` (100vh, 100dvh where supported). The panel's max-height is the visible space between those, `overflow-y: auto; overscroll-behavior: contain`. Look, contents and open / close unchanged.

**Bug 2 (desktop, Map / More with the side column open):** ☰ peeked out from under the rail at the left edge. Cause: the stack is positioned in the viewport-sized `.app`, so a saved bottom-left corner (`.app.fab-bl .fab-stack { left: 16px }`, from Oct 6–7, not the mobile fix) put it under the rail (z 40) and the column; nothing positioned it relative to the visible map. Fix (`index.css`, `LayerFab.tsx`): on wide layouts the saved corner is ignored and ☰ sits in the map's top-right control column directly under zoom / compass (same 36 px size, `--map-ctrl-btn`, 8 px below the column whose height LayerFab publishes as `--map-ctrl-h`); the panel opens to its left with its top on the column's top, inside the map area between the location bar and the playback bar, scrolling internally; the "drag to any corner" hint is hidden there. The stale `.app.wide.fab-bl` chip / sheet offsets went. Mobile placement untouched.

**Follow-up (a518c60, 56c641c):** on the user's instruction the wide-layout panel is tied to ☰ again — its top is the button's top (it had been lifted to the control column's top to gain room) — and menu-check asserts, with the side column open and closed, that the panel itself is fully inside the visible map area, overlaps neither the column nor the rail, and has its top within 16 px of the button's top. 49/50 locally: every desktop case green; the one red is a phone in landscape (844 × 390 with the playback bar), where the tied panel has 34 px of height and its first row is not fully visible — 162 px when lifted to the column's top. ## Oct 8 (night) — playback stutter diagnosed and fixed; Trip routing fallbacks, the 24 h cap, the rain label

**Playback stutter — diagnosis (`scripts/playback-loop-diag.mjs`, headed Chrome, CPU 4×, Fast 4G, APIs and tiles mocked).** Three loops of satellite (19 frames), then radar (16), per loop: tile requests by host, frames switched late (> 1.5 × the 450 ms step), frames shown before their source had loaded ("blank"), rAF frame times p50 / p95 / max, longest main-thread task, JS heap. On the previous build the steady state was fine — phone, loop 3: 0 requests, 0 late, 0 blank, frames 17 / 17 / 21 ms — but the desktop run caught the real mechanism by accident: its window lost focus, the app's "re-poll on tab focus" refreshed the satellite frame list, and **loop 3 made 536 requests (481 GIBS tiles + 55 basemap) with 9 blank frames and a 100 ms frame**. Both layers rebuilt *every* frame source whenever the frame list object changed (the 5-minute refresh, a tab focus after 2.5 min), so every tile was fetched again mid-playback. That is the stutter on "later loops" with live GIBS latency. d45de2b (only the current frame + 2 attached) is not the cause: hidden sources keep their tiles in MapLibre's per-source LRU — the radar loop after a full visibility cycle made 0 requests. GIBS and RainViewer tiles are cached by MapLibre per source; the browser HTTP cache is secondary (the live header probe was refused by the day's RainViewer cap, so expiry is not relied on — see the fix).

**Fix (3 commits):** frame sources are keyed by frame time, so a refresh adds the new frame and drops the oldest and touches nothing else; satellite frames hide like radar (current + next two visible while playing); `refreshExpiredTiles: false` (the time is in every tile URL) and `maxTileCacheSize: 20` per source. **Memory bound:** frames × (tiles in view + 20 cached) × 256 KB ≈ 60 MB (phone, 19 frames) to 120 MB (desktop) of textures for the imagery stack. **After:** the diag forces a frame-list refresh after loop 1 — phone and desktop, satellite and radar: loop 2 ≤ 1 tile request, loop 3 = 0, no late or blank frames, frame max 34 ms, longest task 0 ms, heap 12–20 MB. The check is in prod-suite (headless: requests only) and in the live pass (headed, phone + desktop: requests, no blank frame, no frame over 100 ms).

**Trip / legend:**
1. The fallback line now reads "Using backup routing (OSRM)"; the Valhalla failure detail goes to the console (`[routing] Valhalla failed, using OSRM: …`). No URL in the panel, no overflow.
2. **Urbandale → Miami 400:** one guarded live request reproduced it — `{"error_code":154,"error":"Path distance exceeds the max distance limit: 1500000 meters"}`. The FOSSGIS demo caps auto routes at 1 500 km of path. **Yes, long trips go straight to OSRM:** above 1 400 km straight-line (the path is always longer) Valhalla is not asked, OSRM routes it, and the note says "Long trip: routed by OSRM (the Valhalla demo stops at 1,500 km)". ## Hardest parts, in order

1. **Dead / changed upstream APIs.** The brief named the USGS Water Services instantaneous-values API; `waterservices.usgs.gov/nwis/iv` now refuses connections (decommissioned). Replaced with the USGS Water Data OGC API (`api.waterdata.usgs.gov/ogcapi/v0`), which has a different shape (one feature per *time series*, not per site) and needs a second collection for names. NOAA NWPS keeps flood thresholds only on the per-gauge detail endpoint, so "categories for every marker" costs N+1 requests — solved with a nearest-20 cap, 5-way concurrency and a session cache. RainViewer's public tiles silently return a "Zoom Level Not Supported" image above z7; this only showed up in screenshots, and the fix is capping the raster source at `maxzoom: 7` so MapLibre overzooms.

2. **MapLibre 6 + Vite workers.** MapLibre 6 resolves its worker relative to `import.meta.url`, which breaks both under Vite's dependency pre-bundling (dev) and Rollup chunking (prod). The map rendered black with "Worker failed to load". Fix: import the worker via `?worker&url` and hand it to `setWorkerUrl()`. A second black-map cause was `maplibre-gl.css` overriding my container positioning (`.maplibregl-map { position: relative }` → 0 px tall) — fixed with a more specific selector.

3. **Flood-risk model that is honest and cheap.** Combining three datasets of different resolutions (9×9 Open-Meteo grid, z11 terrain tiles, thousands of NHD segments) into a 28×28 grid on a phone. Everything runs in a worker: terrarium PNGs are decoded with `OffscreenCanvas`, drainage distance uses an exact spherical point-to-segment formula with a bbox pre-filter (784 cells × ~2000 lines would otherwise be ~1.5 M segment tests). Weighting the factors so dry forecasts never light up (rain gate) and so non-US locations still get a meaningful terrain+rain score took several iterations against real locations (Philadelphia dry vs. Manchester in rain).

4. **Nowcast without a nowcast API.** Open-Meteo has no minute-scale nowcast, so the 6-hour nowcast is built in the worker: hourly cloud/rain/wind fields are interpolated to 10-min frames and advected semi-Lagrangian by the wind (with a steering factor and a blend that trusts the model near t0 and advection further out). Rendering: clouds+rain go through a MapLibre `canvas` source, wind through a separate particle canvas so the map itself doesn't repaint 60×/s. `animate: true` on the canvas source made the whole map re-render continuously; switching to `animate: false` + `play()/pause()` around a single frame fixed it.

5. **Popups that can't fall off a phone.** MapLibre's own popup overflows small viewports. The popup is React-rendered, measured, flipped above/below the tap point and clamped to the map container with an 8 px margin, and re-positioned on every `move`. Verified by tapping all four corners in the QA script.

6. **Keeping the map usable while panels are open.** The bottom sheet (peek / half / full) must never cover controls: the FAB, legend, toasts and MapLibre controls are positioned from a `--sheet-h` CSS variable that follows the sheet, and the full-height mode hides the floating controls (the ▼ button brings them back). The first QA run caught the FAB being buried under the half sheet.

7. **Verification with a hidden window.** The desktop's embedded browser pane stops painting when the app is minimised, so screenshots timed out. Switched to headless Playwright + SwiftShader (`scripts/e2e.mjs`, `scripts/qa.mjs`, `scripts/pwa-check.mjs`) for repeatable visual + functional checks.

## Round 3 — block tiling (Sept 30)

The single 60 km "data window" that moved with the map was replaced by fixed geographic blocks (`src/lib/blocks.ts`): 0.5°/1°/2° tiles chosen by zoom, each fetched once, derived products (rain cells, flood cells, nowcast) computed per block in the worker, merged into one MapLibre source per layer via `setData` (no flicker), and cached (30 blocks) so panning back is free. Rain-cell properties are keyed by *absolute hour* and nowcast frames share a store-wide `t0`, so blocks fetched minutes apart still scrub in lockstep. Verified by `scripts/blocks-check.mjs` (9/9: viewport covered, small pans fetch nothing, a large pan keeps overlapping blocks and fetches only the new ones, pan-back is served from cache, continental zoom loads nothing, close zoom switches to the fine level).

Hard lesson: the first cut used 9×9–13×13 points per block and immediately hit Open-Meteo's `429 Minutely API request limit exceeded` — every location counts as a call (600/min). Blocks now use 7×7–8×8 points and `src/api/openMeteo.ts` enforces a rolling per-minute budget with a 429 back-off. NHD queries were also gated (2 concurrent, 1 500 records, 4-decimal geometry) because multi-MB flowline downloads were starving the grid fetches. The flood score also got a 7×7 relative-elevation window, a ±2 m dead-band and a 3×3 smoothing pass to stop the checkerboard on flat terrain.

Production verification (after the hourly quota reset): `scripts/zoom-check.mjs` — 4 level-0 blocks, 49 rain cells + 576 flood cells each, all Open-Meteo responses 200, settled in 58 s. Testing note: the hourly quota (5 000 locations) is easy to exhaust with repeated headless suites from one IP; run them sequentially and expect a cool-down.

Also fixed: a bulk find-and-replace had turned `store.set({ focus: place.lngLat })` into a no-op; the map's own moveend handler had been masking it.
